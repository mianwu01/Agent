## 直接发现

明确要求 agent 替自己测速/查手机模式的两个有害候选是 c003 和 c010；候选成功率分别3/16、4/16，原生分别15/16、16/16；候选后续任意转人工均13/16，原生均1/16。两案独立原生严格委托频率均0/16。

但这个模式不是原生总体不演：s016 和 s034 的独立原生存在36条明确要求 agent 测速的回复。这36条全部失败，下一 agent 动作全部直接转人工。逐案比较如下；同状态重复参考批次分别报告，原始 q 不重复累计。

严格委托支持“双控制下操作归属不清时，agent 往往直接转人工”的模式。它在不同状态的原生频率差异很大：不能把这批证据概括为 collapse 隐藏了这一整类行为。下一步方法比较仍优先完成；若补机制实验，比较同状态、同设备状态的“请你替我测速”与“请指导我自己测速”。

c000“查连接状态”、c009“查其他原因”保留为歧义诊断请求，没有纳入严格委托。只买1GB也没有纳入；此前审计显示其失败同时包含精确容量评分与其他断言未满足，不能全部归因于评分。s010不在这15个固定块频率队列内，未混入计数。

全部15个确认案例已列出。结果文件保存各频率与成功/转人工比例的Wilson95%区间；检测器7项边界核对通过，工具归属由源码机械核对。

## 原生 agent policy 的相关规则

main_policy.md 第13行："You should transfer the user to a human agent if and only if the request cannot be handled within the scope of your actions."
第15行："You should try your best to resolve the issue for the user before transferring the user to a human agent."

因此，直接转人工还涉及 agent 如何解释“请求超出自身动作范围”的政策。下一步配对重测应保留政策，并区分 agent 明确称无工具而转人工，与指导用户执行后仍失败；不要把所有转人工都归为通用能力不足。
